### 2.6 `migration_impact`

**Yes, as declared.** Two forward-only migrations (§35.1): `0003_organizations` — three additive tables, one enum, CHECK constraints, indexes, and foreign keys — and the hardening's `0004_bootstrap_key_shape`, which adds a single CHECK (`chk_organizations_bootstrap_key_kebab`, the key grammar). Nothing in `0001`/`0002`/`0003` is edited (gate G-6/migration-immutability enforces it). Acceptance covers deploy-from-empty (the suite's `test-setup`), upgrade-from-`0002` through `0004` on a scratch database with M1b rows intact, redeploy idempotence, and `prisma migrate diff` drift. `prisma/roles.sql` is unchanged: default privileges already grant the application role DML on migrator-created tables, so no hand-written `GRANT` appears in either migration (G-9: no `GRANT ALL`, no `SECURITY DEFINER`, no `BYPASSRLS`, no `search_path` change, no string interpolation). No RLS policy and no `SET LOCAL` are introduced — those are M2-S4's by §40.6, and the design keeps `organization_id NOT NULL` with organization-leading indexes so RLS lands without obstruction. Rollback is forward-only: revert by a new forward migration dropping the objects this slice added (the three tables, the enum, and the F-3 CHECK), or simply drop the branch — no production database is touched by this slice.

### 2.7 `security_impact`

- **No new endpoint, permission, or session surface** (S-09, AC-23): the OpenAPI document stays byte-identical; the only entry point is a server-side command requiring the operator database credential (§10.4).
- **Authorization model:** possession of `MIGRATION_DATABASE_URL` (operator/migrator role) _is_ the credential; the command fails closed when it is absent and reuses `loadConfig` so a deployment where migrator and application identities collapse (§13.4) is refused before connecting.
- **Data classes touched:** global identity (`users.email`), tenant boundary (`organizations`), tenant-scoped relationships (`organization_memberships`). No credential material, token, or secret column exists after this slice; `users` deliberately has no password field for M2-S2 to fill later.
- **Uniqueness without cross-tenant leakage:** `users.email` and `organizations.bootstrap_key` are global uniques but are exposed through no endpoint (no endpoint exists); organization **names** are deliberately not unique, so no future API can leak another tenant's name through a uniqueness violation (§9.2 T-7's rationale applied to the boundary table).
- **Threat model S-01…S-14** walked explicitly in §3.8 with per-finding PASS/FIXED/BLOCKED/DEFERRED_BY_PLAN classification.

### 2.8 `rollback`

Delete the branch (and, if opened, the PR). The slice is additive: no existing file is rewritten beyond the three deliberately updated db-spec assertions, `schema.prisma` appends, and npm script additions. Database artifacts exist only in local/CI test databases the harness drops after itself; nothing deploys anywhere. Should `0003` ever need reversal in a shared environment, §35.1's forward-only rule applies: a new migration `0004_…` dropping the three objects (data loss acknowledged as the deliberate cost of a wrong slice). `main` stays untouched.

### 3.3 Implementation notes

Six details carry the slice's weight:

1. **Idempotency is a database fact, not a caller flag.** `organizations.bootstrap_key` is `UNIQUE` and the service classifies an existing stored row; an identical retry is a lookup that answers `ALREADY_BOOTSTRAPPED`, never a second insert (AC-01, AC-02). There is no in-memory boolean and no "find / then create" race: the unique constraint is the final arbiter, and a raw unique violation is translated after the transaction with a fresh read.
2. **Racing bootstraps converge by a fixed lock order.** A per-`bootstrap_key` advisory transaction lock is taken _before_ the lookup, then the identity writer takes its per-email lock — always key before email, so the waits form a chain and never a cycle. Four concurrent identical invocations produce one `BOOTSTRAPPED` and three `ALREADY_BOOTSTRAPPED` answers over one durable row set (AC-03).
3. **A conflicting retry is refused without becoming an oracle.** `BootstrapConflictError` carries the operator's own `bootstrap_key` and a reason (`NAME_MISMATCH` / `OWNER_EMAIL_MISMATCH`) — never the stored name or email, so the command cannot be used to probe another tenant's values (AC-04, §9.2 T-7).
4. **All-or-nothing without in-transaction recovery.** Organization, owner user, and owner membership are written in one interactive transaction. PostgreSQL aborts the transaction on the first error, so the service contains no in-transaction error recovery; the one class worth translating (a unique violation) is translated after `$transaction` returns, from a fresh read outside it (AC-05).
5. **The credential boundary is the environment.** The URL is read from `MIGRATION_DATABASE_URL` only — never an argument, never printed, never a fallback to `DATABASE_URL` — and `loadConfig` is reused so the §13.4 role-separation refusal applies to this credential exactly as at startup (AC-08, AC-14).
6. **The post-implementation hardening changed structure and honesty, not behaviour.** F-1 moved the orchestrator out of the tenancy context into a neutral `common/bootstrap/` composition root so the forbidden `tenancy → identity` edge is gone (the tenancy context now owns its own statements in `organization.service.ts`), and added an automated architectural test to keep it gone. F-2 stopped the generic failure branch from asserting "no state was committed" and made it report `BOOTSTRAP_OUTCOME_UNKNOWN` with a retry instruction. F-3 pushed the key grammar down into the database as the `0004` CHECK. The idempotency contract, the lock order, the exit codes, and every acceptance outcome are unchanged (AC-25/26/27).

## 7. Idempotency and concurrency contract

Idempotency is the slice's key acceptance (§40.6), so the exact sequence is recorded:

1. **Normalize** the request (key 3–64 kebab-case, name 1–200 trimmed, email canonicalized) — connection-free, so a malformed request never reaches the database.
2. **Acquire** `pg_advisory_xact_lock(hashtextextended('tenancy:bootstrap-key:<key>', 0))` _before_ any lookup, so racing invocations serialize here.
3. **Classify** an existing committed row for the key: an owner membership must exist (else `BOOTSTRAP_STATE_ANOMALY`), then name and email must match the request (else `BOOTSTRAP_CONFLICT`), else `ALREADY_BOOTSTRAPPED`.
4. Otherwise **create** the owner user through the identity writer's per-email advisory lock (always acquired _after_ the key lock), then the organization, then the owner membership — all in the same transaction.
5. **Commit**, or, on a unique violation that bypassed the locks, **translate after the transaction** from a fresh read (classify the now-committed row, or rethrow untouched).

Consequences: an identical retry is a read (no duplicates); a conflicting retry is a refusal (no adoption); a race resolves to one durable winner; and no code path retries inside an aborted transaction. Both locks are transaction-scoped (`pg_advisory_xact_lock`), so a pooled connection cannot leak one to the next request.

## 9. Bounded-context ownership and dependency direction

§8.4 assigns `users` (and credentials) to **identity** and `organizations` / `organization_memberships` to **tenancy**. Two rules govern how the slice composes them, and the F-1 hardening pass is what makes both hold literally rather than approximately:

- **D-7 (write discipline).** A context never writes another context's tables. Each context now owns every statement against its own tables: `tenancy/organization.service.ts` issues the `organizations` / `organization_memberships` statements, and `identity/user-provisioning.ts` remains the sole writer of `users`. The orchestration that composes them — one atomic operation, both writes inside one transaction — lives in the neutral `common/bootstrap/` composition root, in neither context.
- **D-1 (dependency direction).** §39.3 D-1 states "identity depends on tenancy. Never the reverse." The plan's §39.2 table lists both directions as a stated cycle, and the first implementation resolved the composition by having the tenancy service call the identity writer — which read opposite to D-1's letter. The F-1 hardening pass moved the orchestrator (`organization-bootstrap.service.ts`, its errors, and `bootstrap-cli.ts`) out of `common/tenancy/` into `common/bootstrap/`, so **neither context imports the other in either direction**: `tenancy` imports neither `identity` nor `bootstrap`, and `identity` imports neither `tenancy` nor `bootstrap`. The only cross-context calls in the graph are the composition root calling both writers.

The direction rule is no longer a recorded deviation but an enforced fact: `common/architecture/import-boundary.spec.ts` scans the source tree and fails the build if any forbidden edge reappears (AC-25). D-7's operative write boundary and D-1's letter now agree at the code level, and the earlier alternative rejected in this record — orchestrating from the CLI process entry — is superseded by a typed composition-root service the CLI merely invokes.

## 12. Scope-difference report

Three differences are named rather than silently crossed:

## 15. Deviations

- **D-1 dependency direction (resolved — no longer a deviation).** The first implementation resolved the bootstrap composition by having the tenancy service call the identity writer, which read opposite to §39.3 D-1's letter. The F-1 hardening pass moved the orchestrator (`organization-bootstrap.service.ts`, its errors, and the CLI) out of `common/tenancy/` into a neutral `common/bootstrap/` composition root, so neither context imports the other in either direction, and `common/architecture/import-boundary.spec.ts` enforces it (§9). The §39.2 table's stated cycle remains a plan-level documentation nuance, named here for completeness; it is no longer a code deviation.
- **The database Jest project's per-test timeout in effect is 5000 ms** even though `--showConfig` reports `testTimeout: 120000` (proved by a probe spec during implementation). Because `jest.config.mjs` is outside the slice's `allowed_paths`, the few slow M2-S1 cases carry explicit per-test timeouts instead (AC-03/06/14/18 = 60 s, AC-16 = 300 s). No configuration is changed.
- **PostgreSQL requires explicit `::uuid` casts for text parameters bound against `uuid` columns** through raw Prisma statements (`uuid = text` → SQLSTATE 42883; text→uuid insert → 42804). All uuid-typed parameters in the new db-spec block carry `::uuid`.
- **Prisma reports raw-statement failures as `P2010` carrying the driver's SQLSTATE in the message**, so the acceptance assertions read the SQLSTATE (`23505`/`23503`/`23514`/`22001`) from the message rather than a client-side mapping.
- **An over-length bootstrap key fails as `22001`, not `23514`.** `bootstrap_key` is `varchar(64)`, so a 65-character input is rejected by the column type before the CHECK is consulted; the F-3 `23514` fires for in-range-but-wrong-shape values (`ab`, `Mixed-Case`, `main_shop`, `has space`, `-leading`, `trailing-`, `double--hyphen`). The F-3 acceptance asserts each SQLSTATE on the input that actually produces it, rather than assuming one code for every bad key.
- **The plan's §40.6 M2-S1 row is a derived-criteria exercise.** The plan states the scope and the key acceptance but does not enumerate C1–C9; §3.9 defines them explicitly so the mapping is self-contained and testable.
- **No repair commit, no history operation.** The branch was created by ordinary commits from `3993e424`; nothing was force-pushed, rebased, or reset.

## 16. Residual risks and stated limits

- **RLS is not enforced yet.** M2-S1 delivers the schema prerequisites (NOT NULL, org-leading indexes) but no policy and no `SET LOCAL`; tenant-isolation _enforcement_ (§36.4 I-9) arrives with M2-S4 by §40.6. Until then, isolation rests on the absence of any endpoint and on the operator-only command — stated, not hidden.
- **The command's authorization is credential possession.** There is no second factor and no per-operator identity in this slice; anyone holding `MIGRATION_DATABASE_URL` can bootstrap a tenant. That is §10.4's model (server-side operator credential), and it is bounded by the deployment keeping that credential operator-only.
- **`bootstrap_key` is unbounded in cardinality.** Nothing prevents an operator from creating many organizations with distinct keys; there is no rate limit. This is an operator tool, not a client surface, so the abuse model is the operator credential itself.
- **The default privileges path is relied upon.** The migration issues no `GRANT`; it depends on `prisma/roles.sql`'s `ALTER DEFAULT PRIVILEGES` having granted the application role DML on migrator-created tables. AC-09/AC-11/AC-12 write through the application role and succeed, which is the positive evidence that the default-privilege path holds.
