## 3. Governing decisions taken inside authorized scope

1. **No parallel engine — the count posts through the movement fold (§15.4).** `StockCountService` composes the same `InventoryService` the routes use: posting locks the authoritative level (`lockVariantLevel`, `FOR UPDATE`), computes each line's variance against it, and folds each differing line as `foldMovementInTransaction` — the same 8-step acceptance pipeline, the same `INSUFFICIENT_STOCK` guard, the same §30 costing fold, the same audit writer. The count's movement id **is** the line's id: one line, at most one movement, ever, enforced by a unique index as the structural backstop.
2. **`STOCK_COUNT_ADJUSTMENT` is a produced cause, never a submitted one.** The cause is admissible to the fold but absent from `SUBMITTABLE_MOVEMENT_CAUSES`: the plain movements route refuses it, because a count movement carries facts no bare wire offer could honor (the variance is computed against the *locked* level at post time, the movement attaches to its line, the posting commits inside the count's transaction). `PRODUCED_MOVEMENT_CAUSES` names the distinction; the count document is the cause's only producing execution path.
3. **The count is its own idempotency identity (§38.9.1).** The count row, locked `FOR UPDATE` before anything else, answers the lifecycle: a POSTED count re-posting resolves **REPLAY** (no second effect, no second event), a CANCELLED count answers `409 STOCK_COUNT_CLOSED`. The mutation-ledger idempotency keys the push-level mutation id; the count's own guard answers the storage-level replay.
4. **O-14 at posting, with the reason riding the movement.** A line whose posting would change the authoritative quantity must carry its §38.5 reason code (`409 STOCK_COUNT_REASON_REQUIRED` otherwise — the whole posting refuses, never a partial post); the code travels verbatim onto the produced movement. A matched line (delta zero) needs no reason — an observation that agrees with the system is not a correction.
5. **Cost authority is separate from count authority, and checked inside the posting transaction (§38.5/§30).** Every count route declares only `inventory.count`; when a posting actually offers a cost (an increase on unbased stock), the service escalates through `readEffectiveInTransaction` — the permission is read *in the same transaction that folds*, so revocation between request and post cannot be outrun. A basis-less increase without an offered cost refuses `409 INVENTORY_COST_BASIS_REQUIRED`; a decrease never carries a cost (the engine consumes at the current §30.2 average).
6. **Attachments happen while OPEN; the flip is the last write.** Lines (including the posting's own movement attachments) are written while the count row still says OPEN in the same transaction window — the migration's `stock_count_lines_immutable_when_closed` trigger enforces this at the database layer — and the status flip to POSTED (with its attribution facts, CHECK-pinned to travel together) closes the document in one statement, followed by the single `INVENTORY_STOCK_COUNT_POSTED` event. A posted count's observations are closed history: no line write, no note edit, no status change (trigger-enforced).
7. **Tier 2 applies the whole document inside the ledger's acceptance transaction (§38.22).** `InventoryMutationApplier` maps `INVENTORY_ADJUSTMENT:CREATE` → the fold with its origin stamp, and `INVENTORY_COUNT:CREATE` → create + every recorded line + the posting, atomically: the device cannot half-post a count through sync — the ledger transaction commits the document whole or refuses the mutation. Canonicalization failures map to `REJECTED VALIDATION_FAILED`; domain refusals map to their own closed codes; REJECTED rows are replay-stable and leave nothing applied.
8. **Ingress permissions are re-validated live, and the map is dynamic (§38.16).** `requiredPermissionsOf` returns *all* permissions a mutation needs — `inventory.adjust` (plus `catalog.cost.edit` exactly when the payload offers a cost) for adjustments, `inventory.count` for counts — and the re-validation reads the caller's *current* effective profile server-side, never the snapshot the device asserted. The default applier stays fail-closed for every aggregate no module registered.
9. **The desktop's write door is the outbox, and the producer never decides truth (§38.8).** The producers build the complete immutable payload (decimal strings for `quantityDelta`/`countedQuantity`/`unitCostMinor`, device-generated UUID ids, `?nullable` element grammar for optional members), commit through `OutboxRepository.enqueue`, and perform no drift write and no local inventory arithmetic: the server re-proves every claim at the ledger edge. An O-14-refused posting is *preflight-refused on-device too* (a line without a reason is not enqueued), but the on-device check is an honesty aid — the server's refusal is the law.
10. **The 0015 upgrade proof is part of this slice's definition of done.** M4-S4 assumed `0015` applied; proving what 0015 does to a pre-costing fleet (refuse atomically; recover only through the admin-plane remediation that completes 0015's own artifacts, with the operator's `migrate resolve --applied` bookkeeping, never a file replay) is recorded in `MY_SHOP_M4_S4_MIGRATION_UPGRADE_FINDINGS.md`, probe-scenarios A–G all PASS.
