## 3. Governing decisions taken inside authorized scope

1. **The level is a cache, the ledger is the authority (§15.4).** No code path writes a stock total directly. The only writer is `submitMovement`: fold the exact integer delta onto the locked level, refuse the crossing of zero, append the movement, move the cache, and write the audit event — all in one transaction with one fate. The non-negative CHECK is the database's backstop for a writer that bypasses the service; the level row's `version` counter moves with every fold.
2. **The movement id is the caller's id (§38.14.1).** `POST movements` carries a caller-generated `movementId` that becomes the movement row's own PK. The acceptance decision is answered from the record first: a stored row with that id is answered as a **replay** (the stored submission's response, HTTP 200, no second effect) or — when the same id names a different fact — the ledger's `MUTATION_CONTRADICTION` (409). `answerStored` never needs a preflight SELECT race: the decision is a `findUnique` inside the acceptance transaction, and the database's key is the final word.
3. **Movement POST answers 200, not 201.** The route creates nothing when it is replayed, and the OpenAPI document therefore declared 200; the controller now agrees (`@HttpCode(HttpStatus.OK)`). Every *freshly accepted* response carries the same shape with `status: 'APPLIED'`; a replay carries the stored one. A creation status would make replay answers lie about what happened.
4. **Cause admission is narrower than the vocabulary, exactly like §32.2's event-type discipline.** The database CHECK accepts the full closed §15.5 vocabulary (11 causes); the *service* accepts only the causes this slice has a producer path for — `OPENING_BALANCE` and `MANUAL_ADJUSTMENT` (`SUBMITTABLE_MOVEMENT_CAUSES`, restated by `@IsIn` so the whitelist validation pipe admits the wire shape at all). Every other cause arrives with its owning slice (M4-S4 counts, M5/M6 receipts) — no cause without a producing execution path.
5. **The direction guard is structural, not advisory.** An `OPENING_BALANCE` movement carries a positive delta and none of the outbox/device facts (`chk_inventory_movement_opening_direction`/`_single`), the second opening balance for a (variant, location) is a duplicate refused by the partial unique `stock_movements_opening_balance_once`, and the service maps that real Prisma refusal to `409 INVENTORY_OPENING_BALANCE_DUPLICATE` — resolved by recording an adjustment (§38.5), never by editing the ledger (§38.14.2).
6. **Acceptance order rides the plan's one counter.** `server_sequence` is allocated from the same per-organization `sync_sequences` row the mutation ledger uses (upsert + increment, §38.14.1), unique per organization by index — one acceptance order, whatever later producer writes movements.
7. **Canonicalize before any connection.** The wire offer (cause, exact decimal-string delta ≤ ±999 999 999 999, optional reason/note/document refs) is canonicalized and refused (`400 VALIDATION_FAILED` with field violations) before a single database round trip; the raw wire is never trusted.
8. **The default location is a deterministic guarantee.** `ensureDefaultLocation` materializes the one default on first inventory use; the partial unique `inventory_locations_single_default` makes a second default impossible at the database even for a bypassing writer, so the service's idempotent seed cannot race itself.
9. **Cost is structurally absent, not zero.** `unit_cost_minor` exists (the identity is final) and stays NULL — M4-S3's moving-average engine (§30) is the only producer; the M4-S1 `hasCost: false` marker has its inventory analogue in the NULL column's honesty.
10. **Defence at three depths for the §15.6 guard.** (a) the service's locked fold refuses before anything is written; (b) the guarantee is a transaction-wide `SELECT … FOR UPDATE` on the variant row *plus* a re-read of the level row inside the acceptance transaction, so two concurrent submissions serialize on the same lock before either folds; (c) the database CHECK refuses a negative level from any other writer. Concurrency evidence (§5, §6) is real-parallel submission, not mocked interleavings.

**Wire-shape and schema-agreement decisions worth recording:**

1. **`@HttpCode(200)` on the movement POST** (decision §3-3) is a controller change made to agree with the already-declared OpenAPI response status, not a doc edit to agree with code.
2. **The whitelist-pipe admission.** The global validation pipe runs `forbidNonWhitelisted`, so `cause` — a plain string the domain canonicalizer validates against the closed producer subset — carries `@IsIn(SUBMITTABLE_MOVEMENT_CAUSES)`; a member without a decorator is rejected before the domain runs. The canonicalizer remains the sole authority for the value's *meaning*.
3. **AC-18 agreement, deliberately asymmetric.** `prisma migrate diff` cannot see a partial-index predicate, so a schema-side `@@unique` whose name matched the DB's partial index still read as drift. The derivation is: partial indexes (`stock_movements_opening_balance_once`, `stock_movements_organization_origin_mutation_key`, `inventory_locations_single_default`) are declared **only** by the migration, and the modelable uniqueness — the per-organization acceptance order and the `(id, organization_id)` pairs — is declared in the schema with `map:` names identical to the migration's. The correction FK uses Prisma's default constraint name in the migration itself (`stock_movements_reverses_movement_id_organization_id_fkey`). `migrate diff` exits 0; the drift is *impossible*, not tolerated.
